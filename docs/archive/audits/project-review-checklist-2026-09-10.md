## 4. 三项已复现问题的实施说明

### R1：旧读取在配置保存后回填缓存

**位置：** [client.ts](../../../src/api/client.ts) 第 201–210、302–311 行；实际使用方 [chatApi.ts](../../../src/api/chatApi.ts) 的 `getHostConfig`／`saveHostConfig`／`clearHostConfig`。

**复现顺序：** 启动一个可缓存 GET 并延迟返回；让同 URL 的 POST 成功，把服务端值从 `old` 改为 `new`；再放行旧 GET。随后的 GET 返回 `old`，底层 GET 仅执行一次，而服务端已经是 `new`。正常顺序的“GET 完成→POST→GET”对照可以得到新值，因此这是并发时序问题，不是所有写后失效都失效。

聊天配置明确使用 30 秒内存 TTL，且读取、保存、清除共用 URL，所以有真实调用路径。潜在表现是保存／清除后短时间又显示旧配置；本次未在浏览器复现该页面症状。

**修复方向：** 为资源增加写入代际或失效版本；成功写入后，写前 GET 不得写入新代缓存，写后的读取不得加入旧代 inflight。保留上一轮“取消旧请求立即刷新、旧 finally 不删除新请求登记”的修复。

**验收：** POST 与 DELETE 都覆盖“旧读先完成”“旧读后完成”“写后立即读”“失败写入”“取消并替换”等顺序；不仅断言请求次数，还断言最后可见配置与服务端一致。

### R2：消费者自己的响应校验被跳过

**位置：** [client.ts](../../../src/api/client.ts) 第 201–210、287–294 行。

**复现：** 先缓存 `{ok:true,value:1}`，下一次请求传入恒为 false 的 `validate`，请求仍成功，校验调用次数为 0。同 URL 并发时，后加入者的恒 false 校验也被跳过；直接发起新请求的对照会正确抛出 `invalid-response`。

**修复方向：** 共享层只负责传输、解析及通用 HTTP 错误；每个消费者拿到响应后，单独应用自己的响应契约。不要仅给缓存分支补一行检查而继续遗漏共享分支，也不要让首个消费者的专属校验决定其他消费者的结果。

**验收：** fresh／cached／shared 三条路径均校验；不同消费者的接受／拒绝结果独立；保留 abort、timeout 和替换请求回归。

### R3：可变响应对象污染缓存／其他消费者

**位置：** [client.ts](../../../src/api/client.ts) 的 `awaitShared`、缓存命中返回值与第 303–313 行。

**复现：** 缓存响应包含 `config.engine='original'`；调用方将首次结果改为 `caller-edited`，下一次缓存读取也变成 `caller-edited`，嵌套对象引用相等。首次网络返回直接使用待缓存的 parsed 对象，浅拷贝不能隔离嵌套对象。

**修复方向：** 明确 API 响应的不可变契约，或在缓存／消费者边界隔离对象；对 JSON 数据可以评估深拷贝。先测代表性大响应成本，不机械深拷贝全部业务状态。

**验收：** 修改首个结果的顶层字段、嵌套对象和数组，缓存及其他消费者均不变化；无额外网络请求。当前已确认基础层行为，尚未定位真实页面中会触发该污染的具体修改操作，故列 P2，不夸大为已发生的数据损坏。

## 5. 优化、待实测与内容工作细则

### O1／O2：先把缓存和测试契约写清楚

`cacheTtlMs:0` 或不传 TTL 的请求仍可能读取同 URL 已存在的内存缓存。本次有单独观察记录，但**不把 HTTP `cache:'no-store'` 与内存 TTL 并存本身判作错误**：`chatApi.ts` 正是有意关闭 HTTP 缓存、同时保留 30 秒内存缓存。

建议增加明确的内存刷新策略，例如 bypass／refresh，并明确是否允许加入 inflight；再补可变 headers／credentials 场景的去重键测试。不能直接把所有 `no-store` 当作禁用内存缓存而破坏已有去抖行为。

[client.spec.ts](../../../src/api/client.spec.ts) 已覆盖共享请求、取消替换、TTL 到期与顺序写入失效。本次应在该文件补边界用例，而不是声称“请求层没有测试”。[Vitest 配置](../../../vitest.config.ts) 的全局 lines 17、branches 11 是最低阈值，不是本次实测覆盖率；已有 stores／utils／config／任务中心门槛。建议在新行为稳定后为 API 层单独设置基线，不靠提高一个全库数字制造进步。

### V1：复验 CSP 首次入口，而不是先放宽安全策略

[router/index.ts](../../../src/router/index.ts) 依赖 `aics_csp_strict` 标记，只在 `evalAllowed()` 为 false 时写入；[server/security.js](../../../server/security.js) 为 `/chat`、`/companion` 放行 `unsafe-eval`。源码推断：空 sessionStorage 首次直达 Live2D 页时可能没有 strict 标记，随后离开仍走前端跳转；存储读写异常时也可能丢失该判断。

这是**待浏览器复验的边界风险**，不是本次已证明可利用的安全漏洞。用全新上下文分别测试首页→聊天→首页、聊天直达→首页、桌宠直达→普通页、存储不可用；记录是否请求新文档、当前文档策略和任务确认行为。必要时用可靠的当前文档策略标识和内存状态替代只靠 sessionStorage 猜测，不把 `unsafe-eval` 扩到全站。[MDN 的 script-src 说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/script-src)解释了 `unsafe-eval` 对动态脚本执行的作用。

### C1／C2：提示词优先，人工看图后置

延续用户安排，当前先处理以前写提示词产生的错误，不启动全量人工看图，也不修改 pinned 基线。复用[统一工作流](../../workflow.md)与 [scene-render-contract.js](../../../scripts/lib/scene-render-contract.js)；后者固定使用 Anima，不能仅凭这一辅助结果宣称 SD／WAI、Anima、Krea 的所有提交都一致。

按 scene／blueprint／character／outfit ID 建立逐条差异证据，核对实际发送的正向、负向、服装绑定、镜头和尺寸，定位故事与物件矛盾、服装叠加、正负向抵消及引擎字段差异。静态或编译通过与真实出图通过分开记录；后续确需改 prompt，继续遵守 [AGENTS.md](../../../AGENTS.md) 的真实渲染和定稿保护要求，不能以本次文档审阅替代。

`576e0e1` 合并批次按“已合并、尚未由本次重新验收”记录。新增内容规模应从重建产物重新统计后更新项目状态，不能只根据提交标题推算。聚合数据文件本来就由 [.gitignore](../../../.gitignore) 排除并重建，**没有把 `data/scene-blueprints.json` 提交到 Git 不是缺陷**。只有具备对应 recordId、人工决定和发布 manifest 的图片才能认定已审核／已发布，不能将未看图项目补写为 pass。

### O5／O6：以完整旅程和本地诊断增强体验

沿用现有“角色创作画室”品牌、粒子功能与深浅主题，集中优化角色→场景→生成→入册一条路径的主行动、空态、等待态、取消态和错误文案。验收包含桌面／窄屏、键盘焦点及任务进行中的跨页行为；本次未实际测量点击数或任务成功率，不声称现有界面一定存在这些问题。

[server.js](../../../server.js) 已有本地日志入口，并非“完全没有日志”。可在其基础上增加用户主动导出的脱敏诊断包，串起任务 ID、引擎、数据版本、取消原因和状态迁移。不得默认上传外部遥测；token、API key、敏感提示词、聊天正文和截图应被排除或由用户明确选择。
