## 当前确证缺陷

### A01 / P1：清除一个角色后会覆盖另一角色的新消息

位置：[useChatStorage.ts](../../../src/composables/chat/useChatStorage.ts) 第 140 行，以及第 143–151 行的合并分支。

`state.historiesRevisions[char] || state.historiesRevision` 把合法的角色修订号 `0` 当成缺失。清除宁宁提升了全局修订号，却没有提升夏目的修订号；旧窗口因全局值较大而忽略另一个窗口对夏目的普通更新，随后把自己的空历史写回。

复现：两个存储实例加载同一份内存 localStorage；A 清宁宁，B 给夏目新增一条消息并保存，A 再保存。B 保存后夏目为 **1 条**，A 保存后变为 **0 条**。无需同时执行 JavaScript，只要两个窗口按此顺序操作即可触发。

应区分合法的 0 与不存在的修订号，并用跨角色/跨窗口行为测试验证清除墓碑和普通新增都被保留。

### A02 / P1：加载时写入失败可能清空有效聊天记录

位置：[useChatStorage.ts](../../../src/composables/chat/useChatStorage.ts) 第 259–267 行。

同一 `try/catch` 包住读取、解析、归一化及写回。有效历史已经成功读取，只要归一化的 `setItem` 抛错，就进入“记录损坏”分支并尝试保存空历史；空记录能写入时，原始数据被永久替换。

复现：先保存一条有效历史，仅对下一次聊天记录写入注入 `QuotaExceededError`，再调用 `load()`。原历史从 **1 条变为 0 条**，错误提示为“本地聊天记录损坏，已恢复为空白会话”。这证明写失败分支具有破坏性；本次使用故障注入，没有故意填满用户实际浏览器存储。

应分离解析损坏与写入失败；写失败时保留原始记录和可用内存状态，不用空数据覆盖。

### A03 / P1：远程自定义聊天目标可访问未托管的本机服务

位置：[routes/chat.js](../../../routes/chat.js) 第 174–176 行允许 loopback HTTP，第 253 行发起上游请求，第 531 行聊天入口没有按请求来源约束目标。

复现使用真实 Host/token 中间件与聊天路由，加两个临时 loopback HTTP 服务：携带有效测试 token 与转发头，模拟远程请求。相同目标对 `/api/chat-provider/test` 返回 **403**，对 `/api/chat` 返回 **200**；未托管的本机服务实际收到 `POST /private/chat/completions`，其回复被回传给远程会话。

边界：远程自配公网兼容 API 可能是预期功能；本问题限于远程可触达网关机器上的未托管 loopback 服务。只证明固定 POST 与追加 `/chat/completions` 的路径，不声称任意方法、任意路径、读取文件或命令执行；必须持有效远程 token。

应在服务端区分本机自配、站主授权托管和远程自配目标，覆盖私有目标、DNS 解析及重定向检查，不能只靠前端隐藏本地配置。

### A04 / P2：跨窗口合并会截断正在流式生成的回复

位置：[useChatStorage.ts](../../../src/composables/chat/useChatStorage.ts) 第 64–74、147–148 行；[useChatConversation.ts](../../../src/composables/chat/useChatConversation.ts) 第 141–148、185 行。

合并按 mid 去重但远端旧对象优先，长度变化时替换历史数组；流式回调仍持有原 assistant 对象。流式期间保存一次中间状态，另一窗口读入并新增消息，再触发合并，后续 token 会更新已经脱离当前历史的对象。

复现：原助手对象最终内容为 `first token plus more finished`，最终持久化内容只有 `first token`。中途调音量/修改草稿等操作会调用 `save()`，因此中间快照不是仅存在于测试中的路径。

应保持正在生成消息的身份与更新顺序，覆盖流式中途保存、另一窗口新增、最终保存和重新加载。

### A05 / P2：角色生图工具没有下发任务却报告成功

位置：[routes/desktop-tools.js](../../../routes/desktop-tools.js) 第 276–350 行；[useChatConversation.ts](../../../src/composables/chat/useChatConversation.ts) 第 268 行。

工具只组装字段并写 JSON，没有调用生成引擎或任务队列；写元数据失败也被吞掉。返回值仍为 `ok: true`、“已成功…下发生图任务”及 PNG 路径，前端据此增加好感。

本次在隔离临时工作区执行工具，观察到 **ok=true、PNG 不存在、目录仅有 JSON**。对生产 `server/services/routes/src` 的调用链检索没有找到消费该 JSON 的生成接线。这是任务未下发的问题，不能解释为办公机缺 GPU 导致生成慢。

应接入真实受控任务并如实返回状态，或明确返回仅准备了草稿；不能提前报告任务成功或奖励。接线的真实出图验收仍需主力机。
