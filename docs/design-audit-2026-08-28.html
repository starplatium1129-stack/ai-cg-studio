02值得捍卫的三件事

先说好话，因为这三点在个人项目里真的罕见，别在后续重构里把它们弄丢了。

强项

101 个手绘双线图标，统一渲染器，零 emoji 污染

不是描边图标，是手绘双线：主笔 stroke-width 1.8，副笔 1.2 + translate(0.55 0.45) rotate(1.2 12 12) 制造微妙错位，再加端点墨点 r="0.52"。这个技法组合出现在 ArchiveIcon.vue:5-32，101 条图标定义全部由它单一渲染输出。全项目 .vue 模板里的 emoji 渲染是 0。SceneExplorerView.vue:276-284 那张 emoji 映射表是服务端历史数据的兼容层，不是违规。

这套东西的辨识度，比你再加十层光斑都值钱。

强项

深色主题是被设计过的调色板，不是浅色反色

证据在注释里就已经说明意图：底色从 #110b22 紫黑 ↔ #f8eef4 粉白（design-system.css:16 / :263）；accent 在深色下是提亮的 #f4a6d7、在浅色下压深为 #a04472（:40 / :276），而不是简单取反；阴影在浅色下整体换成粉紫 rgba(158,90,130,0.10)，注释写"读作纸影，不是灰雾"（:291-293）。

这是有色彩判断力的人做的活。问题只在于浅色那半边没做完。

强项

reduced-motion 覆盖 43 处，包括关停 Live2D 的 WebGL ticker

全局短路在 design-system.css:500-505；JS 侧动效有 utils/motionPreference.ts:3-7 兜底；最妙的是 composables/live2d/context.ts:24-28 主动关停 WebGL ticker —— CSS 管不到的部分也想到了。很多商业项目都做不到这个密度。

03P0 · 会实际伤到你的四个问题

按"你真的会看见它出问题"排序，不是按代码洁癖排序。

P0

浅色主题只完成 32.5%，--danger 完全没有浅色覆盖

:root 定义了 154 个令牌，[data-theme="light"] 只覆盖了 50 个。success / warning / info 三个功能色在浅色下都被压深过（design-system.css:305-307），唯独 --danger 漏了 —— 浅色模式下危险态继续沿用 #EF5350。而 --danger-text: #a81f1c（:53）的存在恰恰证明这块是被认真处理过的，danger 只是被落下了。

同时未覆盖的还有 --archive-paper、--archive-ink、--mood-joy..warmth 原色、--r-dossier、--r-terminal。

最小修复：补一行 --danger: #c62828; 到 design-system.css:304 附近。30 秒的事。完整的浅色策略见第 05 节建议 1。
P0

20 套角色主题里 17 套没有浅色版，切过去会炸

director/tokens.css:40-139 用 @property 注册了 6 个可动画自定义属性，给 20 个角色各配了 6 个色值，并用 transition: --character-accent .62s 做整树渐变 —— 实现本身很漂亮。但浅色覆盖只有 default、natsume、triad 三处（:140-154）。

结果是：切到浅色主题时，asuka 的 #ff4a3d、megumin 的 #ff4757 这类深色底高饱和值会直接压在粉白纸上。作为角色厨，你在角色页停留的时间可能比任何页面都长，这是最容易撞上的视觉事故。

建议：先按建议 1 决定浅色主题的去留，再决定是补 17 套还是删掉 3 套补丁。别在方向未定时就动手补色。

design-system.css:1086-1093 用 .btn:disabled { opacity: .45 }。降 opacity 会同时压掉前景与背景的差值，我按 alpha 合成重算了实际渲染结果：

04P1 · 工程纪律正在被侵蚀

这些问题你今天看不见，但它们决定了半年后这套设计还改不动得动。

P1

动画门禁全绿，但它只检测了 1.9% 的违规

npm run lint:animations 只扫 transition 值里的布局属性（width/height/top/left/margin/padding/max-*/min-*）。实际扫出 4 处布局违规，脚本抓到 3 处（design-system.css:1197 .meter-fill、CharacterView.vue:700 .bg-story、SceneExplorerView.vue:771 .ex-more），豁免基线 ALLOWED_EXEMPT=3 恰好持平。

漏掉的是 design-system.css:1778 的 .anim-collapse-grid { transition: grid-template-rows 220ms } —— grid-template-rows 是逐帧重排属性，但不在 lint-animations.js:42-48 的名单里。

更关键的是：29 处 box-shadow + 14 处 filter 过渡完全不在检测域内。这两类都会触发逐帧重绘，filter 还要离屏合成，比 width 贵得多。

修复：给 lint-animations.js 的白名单补 grid-template-rows/columns，并把 box-shadow、filter、backdrop-filter 加为"警告级"检测（不计入豁免基线，但会打印清单）。改之前先把当前 43 处加豁免注释，否则门禁会立刻变红。
P1

32% 的过渡时长绕开了 7 档令牌

7 档语义令牌定义在 design-system.css:199-205（120/160/200/260/320/420/560ms），令牌引用 463 次 —— 但 --motion-hover 独占 369 次（79.7%），实际是单档塌陷，另外 6 档形同虚设。

硬编码时长 215 处，UI 反馈级的散落为：.3s×11、.2s×10、180ms×8、.22s×8、.5s×7、.45s×7、220ms×4、140ms×4。180 紧邻 160、220 紧邻 200 —— 这种无意义偏差最难维护，因为看代码的人无法判断它是有意为之还是手滑。

修复：把 180→160、220→200、.3s→320ms、.2s→200ms、.5s→420ms 做一轮批量归一。这是纯机械替换，风险极低，收益是动效节奏真正统一。
P1

行高零令牌化 —— 有字号阶梯，没有行高阶梯

字号是纪律最好的一块：15 档全 rem（design-system.css:136-151），裸 font-size 仅 9 处。但 --lh-* 定义了 0 个，85 处裸值散布在 12 种取值上：1 / 1.4 / 1.45 / 1.5 / 1.55 / 1.6 / 1.65 / 1.7……

对中文排版来说行高比字号更影响观感。1.5 和 1.55 的差异肉眼几乎不可辨，但会让整站节奏发飘。而且 DESIGN.md 里已经写死了 body 行高 1.7、heading 1.3、label 1.4 —— 三档就够了。

修复：加 --lh-tight: 1.3 / --lh-normal: 1.6 / --lh-loose: 1.7 三档，按 DESIGN.md 的定义批量替换。
P1

圆角 12 个值，且注释与代码互相矛盾（AI 协作高危）

圆角令牌：--r-xs:4 / --r-sm:8 / --r-md:10 / --r-lg:14 / --r-xl:16 / --r-2xl:20 / --r-3xl:22 / --r-stage:24 / --r-pill:999（:169-174），外加 --r-dossier:14、--r-terminal:6、--r-brand-mark:7px 12px 7px 12px。--r-dossier 与 --r-lg 同为 14px，属无注释的实质重复。

真正危险的是这一处：design-system.css:165-166 的注释写着"md 8→4 / lg 12→6"，但 :169 的实际值是 --r-md: 10px; --r-lg: 14px。注释记录的是一次已被覆盖的历史变更。

你这是 AI 重度协作项目（AGENTS.md 里有硬红线和门禁），AI 会优先相信注释。一条撒谎的注释会让后续所有由 AI 执行的样式改动都基于错误的基准值。这类问题比任何视觉瑕疵都贵。

修复：删掉 :165-166 的过期注释（变更史移到文件底部 changelog）；--r-dossier 合并进 --r-lg。建议再加一条门禁：扫描令牌区注释里出现的数字与紧邻声明的实际值是否一致。
P1

断点 16+ 种，三组近似重复值

实测断点：2560 / 1381 / 1380 / 1200 / 1050 / 1040 / 1000 / 960 / 900 / 860 / 768 / 760 / 700 / 680 / 640 / 600 / 560 / 520 / 480 / 460 / 420。

其中 768 与 760（各出现 8 次和 5 次）、640 与 600（各 4 次和 6 次）、480 与 460（各 3 次）—— 三组是彼此相差不到 20px 的近似值。这意味着在两个断点之间，页面会进入一个没人测试过的中间态。

修复：收敛为 5 档 1200 / 900 / 768 / 600 / 480，近似的往主档并。真正需要特殊处理的大屏（2560）和小屏（420）保留。
P1

加载态两套并存，@keyframes spin 重复定义

骨架屏只覆盖 6 个文件 17 处（SceneCard.vue:16、GalleryView、PopularSceneExplorerView、ZoomableImageViewer 等），其余页面各用各的旋转指示器。@keyframes spin 在 design-system.css:1535 和 ControlView.vue:586 各定义了一次；ArchiveStatePanel 又用了自有的 state-orbit/state-counter。

顺带一提 ArchiveStatePanel.vue 本身设计完成度很高（6 态、手绘图标、双环反向旋转、等宽大写状态码、aria-busy/role=alert 齐全、reduced-motion 降级），但全项目只有 2 个文件在用，24 处匹配的空态大多是各页面手写的。

修复：删掉 ControlView.vue:586 的重复定义；把 ArchiveStatePanel 推行到剩下的手写空态（这是纯替换劳动，可以直接交给 AI 批量做）。

06给你这个人的五条建议

以上是通用工程审计。下面这部分只对你成立 —— 你是单人使用的重度二次元用户，这会改变很多结论的优先级。

为什么"单人使用"会改变结论

企业里做设计系统，一致性是为了让 20 个人写出一样的代码。你没有这个问题 —— 一致性对你唯一的用处是让 AI 能可靠地帮你改（你有 AGENTS.md、有硬红线、有门禁，这就是典型的 AI 协作项目）。所以令牌纪律的价值不在"规范"，而在给 AI 一份不会骗人的契约。

反过来，那些"为了团队协作"的负担，你完全可以砍掉。下面第一条就是这个意思。

建议 1 · 浅色主题：我建议你砍掉，而不是补完

个人项目维护两套完整主题是纯负债。你的 154 个令牌本来就是为深色写的，浅色是后补的 50 个补丁 —— 从注释时间线能看出来（深色 2026-07-31 重塑，浅色 2026-08-01 粉嫩化）。补完意味着把 104 个遗漏变量 + 17 套角色色再写一遍，而且以后每加一个新颜色都要写两遍。

方案 A · 锁定深色，把浅色收起来推荐
默认深色，把 AppThemeToggle 隐藏或降级到设置页深处，删掉 50 个浅色覆盖与 3 处角色浅色补丁。省下的时间去补第 3 条建议里的东西 —— 那才是情绪价值真正的来源。作为二次元用户，夜间创作本来就是主场景。
方案 B · 补全浅色
补 --danger + 17 套角色色 + 其余 104 个变量，约 3–5 小时纯机械劳动（可交给 AI，但每套颜色你得亲自看过效果）。

判断依据很简单：如果你白天也常用它（比如在工位上改 prompt），选 B；如果只在晚上创作，选 A。别因为"有切换按钮就应该能用"而选 B —— 那个按钮是你自己加的。

建议 2 · 装饰层已经开始抢戏了，画面才是主角

我把首屏同时挂载的装饰层列一下：

HomeView 首屏：
  .hero-character × 2   每个带 transform .6s + filter .6s + drop-shadow(0 24px 28px)
  .hero-orbit / .hero-watermark / strip-scroll / pop-scroll
全局常驻 fixed 图层（design-system.css:399/403/476/493）：
  float-orb 18s   42rem 见方，filter: blur(2px)
  float-orb 22s
  starfield-float 16s
  bokeh-drift 26s

四个全屏 position: fixed 图层常驻动画，其中一个是 42rem 见方带 blur 的。而你在 DESIGN.md:425 自己写过：

"Do not add decorative whitespace, glow, blur, gradients, or floating shapes without a hierarchy or storytelling purpose."

以及 DESIGN.md:238："Large blank zones with no communicative purpose are a layout defect."

现在首屏的实现与这份自述是矛盾的。对一个创作者来说，最贵的屏幕空间应该给画面，不是给光斑。

具体动作：① 全局氛围层 4 → 2（保留星野 + 一个光斑，砍掉 bokeh 或第二个 orb）；② 给装饰层加 contain: strict 与 will-change: transform（现在 contain 是 0 处）；③ hero 区的 filter: drop-shadow 换成静态 box-shadow，省掉每帧离屏合成。

但 grep 零命中的是这三类：速度线、集中线、拟声词、repeating-linear-gradient（manga 只出现在数据文件里，不是 UI）。

这三类恰恰是日系辨识度最高、成本最低的元素，而且纯 CSS 就能做：

集中线（生成完成瞬间的闪光）
  repeating-conic-gradient(from 0deg,
    transparent 0 2deg, var(--accent-glow) 2deg 3deg)
  + 径向遮罩收边

速度线（队列进度条）
  repeating-linear-gradient(105deg,
    transparent 0 6px, var(--accent-soft) 6px 7px)

拟声词（生成完成）
  --font-display + skewX(-8deg) + 集中线背景
  「ドンッ」「キラリ」「ポンッ」按事件类型切换

这比再加一层光斑有效得多 —— 光斑是背景噪声，集中线是事件。而且它天然符合 DESIGN.md:425 的规矩：它有明确的叙事目的（标记"生成完成"这个瞬间）。

建议 4 · 手绘感只做了一半：图标是手绘的，容器是 Apple 的

全项目 backdrop-filter 用了 142 处，其中 companion.css 独占 35 处。玻璃拟态是 Apple / Notion / Figma 的语汇 —— 而 DESIGN.md:423 白纸黑字写着：

"Do not imitate Apple, Figma, Notion, or a generic anime site as an end goal."

现在的割裂感是：图标是手绘的（有笔触、有错位、有墨点），容器是玻璃的（圆角规整、半透、带模糊）。两种语汇没有对话。

有意思的是，你自己已经埋了答案 —— --r-brand-mark: 7px 12px 7px 12px（design-system.css:171）这个不对称圆角，说明你本来就想要"手绘的不规整感"，只是没推开。

试点方案：卡片/面板用不对称圆角（border-radius: 14px 12px 15px 13px）+ 1.5px 实描边，替代玻璃填充。先在导演台的 CTA 上试点，别全站铺 —— 玻璃拟态在导航和浮层上是有功能的（分层），砍掉反而会丢信息。

建议 5 · 角色主题是杀手锏，但只做了 20 / 40+

director/tokens.css:7-12 用 @property 注册 6 个可动画自定义属性，:26-33 用 transition: --character-accent .62s 实现整树渐变 —— 切换角色时整个界面会像换季一样过渡过去。这个实现很漂亮，是项目里最"二次元"的一处设计。

但它只配了 20 套，而项目有 40+ 热门角色。作为角色厨，剩下那 20 多套的边际情绪价值极高 —— 每个角色有自己的界面配色，这种"专属感"正是私人工具相对于公共产品的最大优势。

成本是纯机械劳动（每套 6 个 hex），可以交给 AI 批量生成，但每套颜色你得亲自看过效果，尤其是它跟立绘、跟深色底的配合。

前置条件：先按建议 1 决定浅色主题的去留。否则每个新角色都要配两遍色，20 套变 40 套。
