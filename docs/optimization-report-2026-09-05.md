## 2. 优先处理的五项问题

优先级定义：P1 为应优先安排的正确性或交付可靠性问题；P2 为随后处理的性能、体验和维护问题；P3 为持续治理。本次未依据有限抽查强行给出 P0 或综合打分。

### P1-01：数据请求失败被当成成功，普通重试无法恢复

**证据：** [sceneStore.ts:133](E:/code/2/lora/AI-CG-Studio/src/stores/sceneStore.ts:133) 中多个元数据请求各自 `catch` 后返回空数组或空对象，随后无条件设置 `metaLoaded = true`。完整加载继续设置 `loaded = true`。

使用当前源码、真实 Vue/Pinia 和受控 fetch 复现：让 `characters.json` 首次返回 503、场景分片正常，结果为 `loaded=true, error=null, characters=0`。恢复接口后再次普通 `load()`，仍为空，角色文件累计只请求一次。

**影响：** 临时网络故障可能表现成角色或蓝图消失，用户得不到可重试的错误提示；整页重开或显式强制刷新才可能恢复。

**建议：** 区分必需数据和可选元数据；为资源保留独立加载状态。必需资源失败不能标记完成，已有成功数据应保留，并提供明确的重试入口。

**验收：** 覆盖“首次 503 → 恢复成功”“部分资源失败”“已有数据后刷新失败”。失败可见、恢复无需刷新整页，不重复请求已成功资源。预计 0.5–1 人日。

### P1-02：不同角色的并发请求错误地共用同一个进行中任务

**证据：** [sceneStore.ts:168](E:/code/2/lora/AI-CG-Studio/src/stores/sceneStore.ts:168) 在判断目标角色之前执行 `if (inflight) return inflight`。同样逻辑也用于核心场景加载。

源码复现 `Promise.all([loadCharacter('nene'), loadCharacter('natsume')])`：没有请求夏目分片，最终只有 shared 与 nene 数据。现有测试只覆盖相同角色的并发去重。

**影响：** 在调用重叠时，后一次切换意图可能被忽略。已复现 store 层行为，尚未测量实际用户操作中的发生频率。

**建议：** 按资源键去重请求，并将“数据缓存”与“当前展示目标”分开管理。旧请求返回后，只有仍与当前目标匹配的结果才可更新视图；强制重载也需要对数据赋值和 loading 状态做代际检查。

**验收：** 覆盖同角色去重、不同角色并发、快速往返切换、慢旧响应晚于新响应四类场景，保证最新意图最终生效。预计 0.5–1 人日，可与上一项合并实施。

### P1-03：“全量门禁”与实际综合检查并不等价

**证据：** [gate-quick.js:166](E:/code/2/lora/AI-CG-Studio/scripts/maintenance/gate-quick.js:166) 的 full 分支调用的是 `QUALITY_TEST_SUITES.check` 文件列表，而不是 `npm run check` 的 21 步编排。对照 [run-check-parallel.js:22](E:/code/2/lora/AI-CG-Studio/scripts/maintenance/run-check-parallel.js:22)，full 没有显式执行相同的后端类型检查、ESLint、场景优化/分级校验、内容校验、参考 URL 检查等完整步骤。

另外，full 在阶段失败后直接跳过后续阶段，`--all` 仅作用于内部文件套件，不能确保继续收集所有阶段的失败。

**影响：** 同一个“全量通过”说法可能对应不同检查集合。当前 full 本身也可能因其他失败退出；这里指出的是覆盖缺口，并未声称本次 full 已通过。

**建议：** 复用一份声明式步骤清单生成本地门禁和 CI 检查；清楚区分“提交前相关检查”与“发布检查”。报告结果带提交号、完成时间、已跑/未跑/失败列表。现有本地钩子策略无需因本报告擅自改变。

**验收：** 用测试证明 full 包含全部发布必需步骤；故意触发任一必需检查，full 均应失败；`--all` 在阶段失败后继续收集其余结果。预计 0.5–1 人日。

### P1-04：角色已入库，但服装参考资产未完全接通

**证据：** 参考 URL 检查发现 112 / 1,448 条缺文件。樱岛麻衣丝质睡衣、初音祭典浴衣各抽查一个链接，服务端均返回 404。参考根目录实际指向 `E:/code/2/lora/AI/CharacterReferences`，不能只统计项目旧 assets 目录。

按 `character.id + outfit.id` 对照参考库 `outfitId`，544 个热门服装中有 **212 个 ID 未匹配**。这是注册或命名映射缺口，不能据此断言 212 套都没有图。参考档案已有 111 个人物条目，因此“有人物档案”不能证明“每套服装都完成参考库接入”。

**建议：** 在现有角色接入流程中输出逐服装验收表，核对数据、主题、立绘、头像、四视角定义、实际文件与 URL。缺口分别标注命名漂移、尚未渲染、未登记。先使用现有修复脚本的 dry-run 审核结果；该脚本还会移除幽灵形态，不宜仅以让断链数字归零为目标直接批量执行。

**验收：** 当前已发布参考 URL 全部可达；每套受支持服装有明确的参考库映射或公开的待完成状态；pending 设计图单列，不混算完成率。预计 1–2 人日完成对账与工具完善，补图耗时需依据缺口和真实渲染速度另估。

### P1-05：内容事实源、编译入口与测试契约正在漂移

**证据：** 当前 unit 套件检测到夏目身份词在前端与样张脚本之间不一致：[promptBuilderStore.ts:115](E:/code/2/lora/AI-CG-Studio/src/stores/promptBuilderStore.ts:115) 与 [generate-showcase-candidates.js:94](E:/code/2/lora/AI-CG-Studio/scripts/maintenance/generate-showcase-candidates.js:94) 使用不同词组。故事对齐检查还列出 58 条潜在不一致，其中 2 条受定稿保护；分级检查计算出 60 条建议变化。

**解释：** 这些数字是规则检查结果。故事关键词可能误报；60 条变化还涉及分类、usage、negative 等字段，不能称为“60 个错误评级”；未进行真实渲染，不能断言 58 张图均有问题。

**建议：** 让前端和离线样张脚本复用同一版本的身份与编译规则，记录生成请求的引擎、模型、参数、数据版本和编译结果，以便复现。逐项判断是内容、描述还是测试契约过时。涉及实际内容变更时按项目现有逐条验收与定稿保护流程处理。

**验收：** 同一角色、服装、蓝图、引擎与参数，两个入口得到一致的编译结果。待核项逐条关闭并附理由；涉及画面判断的结论附真实样张证据。预计 1–2 人日收口规则入口，内容复核另计。

## 3. 第二阶段优化清单

### P2-01：提高测试信号质量，补齐实际失效边界

本次至少有几类不同原因，必须分开处理：

| 类别 | 实测证据 | 改进方式 |
|---|---|---|
| 过时的数量断言 | 画师测试期望 44，当前实际 52 | 从当前配置验证唯一性、可用性和组合规则，避免把目录增长当故障 |
| 绑定源码位置的断言 | 资源调度测试只在 control.js 搜服务路由，但它们已移至 control/services.js 并注册 | 验证实际路由注册与响应行为；保留必要架构约束 |
| Windows 清理失败 | repo-hygiene 在两次检查中均因临时目录 ENOTEMPTY 失败 | 检查子进程退出和文件句柄释放，加入有界清理重试，保留原始业务断言结果 |
| 环境或实现尚待区分 | 受控 ComfyUI/reForge 停止测试期望 stopped，实际 external-or-stopped | 在相同 Windows 权限条件下核对进程身份识别；本次不能直接推断生产服务无法停止 |
| 测试未覆盖的行为 | 158 个前端用例通过，但本报告仍复现两个 store 缺陷 | 优先增加失败恢复、不同键并发和旧响应覆盖测试 |

覆盖率门槛目前全库 lines=5%、branches=3%，本次分别为 8.98%、5.58%。应按关键模块逐步提升；Vue 页面主要依赖 E2E，不能将全库低单测覆盖率等同于“整个系统只有 9% 被测试”。[配置依据](E:/code/2/lora/AI-CG-Studio/vitest.config.ts:29)。

### P2-02：首页展示少量精选，却加载完整创作目录

[HomeView.vue:390](E:/code/2/lora/AI-CG-Studio/src/views/HomeView.vue:390) 调用完整 `sceneStore.load()`；store 同时请求所有元数据和三个场景分片。仅 `scene-blueprints.json` 就有 **3,470.9 KiB 原始 JSON**，本次即时 gzip 约 735.7 KiB。它只是初次目录负担的一部分，压缩后仍需浏览器解析完整数据。

建议首页加载精选摘要和角色目录，蓝图详情随角色或创作页面进入时加载；先拆开元数据职责，避免仅将 load 改为 loadCore 后仍全量拉取蓝图。大型只读目录是否改用浅响应式，应在定位解析与响应式开销后决定。按需拆分和减少大型不可变数据的响应式开销有 [Vue 官方性能文档](https://vuejs.org/guide/best-practices/performance.html) 支持。

**验收：** 首页正常展示当前精选与角色入口时不请求完整蓝图文件；记录优化前后同机冷加载的请求字节数、数据就绪时间和长任务。建议以实测至少减少 50% 的首页目录解码字节为目标，目标并非已实现收益。

### P2-03：预算应覆盖真实加载依赖，大页面按职责继续拆分

生图台路由 138.1 KiB，已接近上限。当前预算统计路由自己的 JS 文件，没有给入口 JS 和共享静态依赖设置同等预算。[预算脚本](E:/code/2/lora/AI-CG-Studio/scripts/maintenance/check-bundle-budget.js:51)。

本次根据新构建 manifest 递归去重计算：入口及其静态 JS 依赖约 **340.1 KiB**；HomeView 自身约 14.9 KiB，但其静态依赖闭包约 **368.5 KiB**。后者包括入口及共享模块，未包括额外布局、字体、图片或动态请求；两者不能相加，也不是网络传输时间测量。入口静态链中可见约 94.1 KiB 的 prompt 和 63.6 KiB 的 live2d 命名块；后者并非 923.4 KiB 的渲染依赖包。

建议对入口和关键路由新增去重后的依赖体积监测，借助现有 `build:analyze` 识别不必要的入口导入。优先拆生图台批量工具、结果管理及专家控制，再处理其他大页面。现行单体门禁已通过，但基线中仍有 20 个历史大文件，包括生图台、作品册、分镜编辑器等。

**验收：** 生图台路由逐步降至 126 KiB 以下的 90% 告警线内，同时入口和依赖总量不回涨；保持现行基线只降不升。不要用把逻辑搬进一个同步共享块的方式制造“路由变小”的表象。

### P2-04：浏览器用户会收到与自己无关的桌面更新错误

本机浏览器首页与生图台实际显示“更新检查失败：仅桌面端支持自动更新”。[DesktopUpdateBanner.vue:19](E:/code/2/lora/AI-CG-Studio/src/components/DesktopUpdateBanner.vue:19) 挂载即检查，[useDesktopUpdater.ts:40](E:/code/2/lora/AI-CG-Studio/src/composables/useDesktopUpdater.ts:40) 将不支持桌面更新当成错误。

建议把平台能力作为显示条件：普通浏览器不呈现桌面更新横幅；桌面端保留真实失败提示与重试，并在重试成功时清理旧错误。

**验收：** 普通浏览器首页和生图台无此错误，桌面更新发现、失败、重试、安装流程仍可正常工作。此项约 0.25–0.5 人日，可提前作为快速修复。

深色 UI 的自动对比度门禁本次通过，已有场景/专家两层模式。视觉抽查不足以支持全站改版结论；优先处理这类可见的错误反馈及实际缺图。

### P2-05：按语义改进轮询，避免机械替换所有定时器

[useCharacterRoomSession.ts:391](E:/code/2/lora/AI-CG-Studio/src/composables/chat/useCharacterRoomSession.ts:391) 每 1.8 秒发起操作状态查询，新查询会先中止上一请求。当响应持续慢于间隔时，存在旧请求反复被打断、完成状态迟迟读不到的条件性风险。

Anima 状态轮询也可结合页面可见性、并发上限和退避统一到现有 `usePolling`。不过聊天的 `startTurnWatchdog` 是本地超时看门狗，并非网络轮询，不能因为用了 setInterval 就列为必须迁移的技术债。

建议完成一次查询后再安排下一次，并约束卸载后回写；现有底座也需核查异常处理和在途请求取消语义。长耗时任务的固定间隔风险可参照 [MDN setInterval 说明](https://developer.mozilla.org/en-US/docs/Web/API/Window/setInterval#ensure_that_execution_duration_is_shorter_than_interval_frequency)。

**验收：** 模拟 3–5 秒状态响应，最多一个进行中查询，操作最终能完成；页面卸载后不更新状态。此项是源码推导的慢响应风险，未开展真实弱网长时间试验。

### P2-06：预压产物清理逻辑与报错修复建议不一致

本次数据校验发现 **18 个源 JSON 已删除的 .br/.gz 文件**。校验提示“重跑 precompress”，但 [precompress.js:92](E:/code/2/lora/AI-CG-Studio/scripts/maintenance/precompress.js:92) 只遍历仍存在的源文件，没有对孤儿压缩产物做成对清理。常规预压不能依靠重新生成不存在的源文件解决此问题。

建议在现有脚本内加入限定目标目录的孤儿检测和清理预览；同时考虑源文件缩小到压缩阈值以下时的旧压缩文件处理。检查模式应验证压缩内容与源内容一致性，而不只是压缩文件存在。

**验收：** 覆盖源文件删除、缩小、内容变化三种情况；不存在旧压缩内容被误用，校验给出的修复步骤实际有效。预计 0.5 人日。

## 4. 建议实施顺序与验收终点
