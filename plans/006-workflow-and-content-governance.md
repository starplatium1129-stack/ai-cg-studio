# 006：工程工作流与内容数据治理规划

> 2026-09-12 建立。本次仅规划，不执行内容修改、资产生成、生产数据迁移或发布。优先级见 [未来规划](../docs/roadmap.md)。
> 进度：D5 第一批（稳定 ID 分配、保存基线冲突、增量分片、完整性校验）2026-09-12 在办公机实施并通过隔离测试；其余阶段待实施。

## 目标与边界

让新增、修改和退役人物／服装／场景时，能明确找到源数据、预览影响范围、选择必要校验并追溯交付证据。保留现有技术栈和工作流入口，不默认建设新 CMS，不因条目增多就把静态内容迁入数据库。

与 [005 架构计划](005-desktop-architecture-consolidation.md) 区分：005 负责桌面布局、状态接口、用户作品持久化与任务恢复评估；本计划负责工程执行流程以及项目自带内容目录的治理。两者复用基础能力，不建立重复的任务或存储系统。

机器分工沿用用户确认：办公机实现、隔离数据／模拟上游测试；主力机真实模型、GPU、桌面设备验收。主力环境为 4K / Windows 150% 缩放。性能改动先测实际瓶颈。

## 当前基线与判断

本次只读统计聚合文件：角色档案 160、热门角色 158、服装 971、通用场景 302、蓝图 1692。对蓝图角色 ID 及已填写的服装 ID 做指向检查，没有发现悬空引用。该结果不代表全部字段、源与聚合一致性、语义或图片质量通过审核；后续开工重新核对。

已有能力应复用：

- `data/scenes/`、`data/popular/`、`data/blueprints/` 分片与 manifest，聚合产物和 DATA_VERSION。
- `scripts/lib/*-store.js`、内容与角色契约、定稿保护、参考索引校验。
- `sceneStore` 统一加载、缓存及角色分片读取。
- 参考和样张的登记、生成、审核、修复、人工决定与发布入口。
- 统一工作流、分层门禁、隔离网关验证、CI、桌面部署唯一入口。

主要维护成本：角色跨多个数据域的职责与重复信息、分级字段间的含义映射、人工审核与资产证据、变更影响范围及跨机器交付状态。不要把这些问题简化为 JSON 文件数量问题。

## W1：工作流执行条件与命名

检查 `scripts/workflow.js`、runner 与 `docs/workflow.md`，逐项明确：

- 允许在哪类环境执行：办公机／GPU 主力机／原生设备／CI。
- 操作性质：只读、隔离测试、写源数据、调用模型、安装、发布。
- 前置条件、输入输出、必要参数、是否支持预览和失败后能否续跑。
- 解释 `check:quick` 与 `gate:quick` 的差异；明确各 `full` 命令是否包含构建、发布预览或真实安装。

默认复用已有描述和校验，不先假定要新增所有元数据字段。若采用结构化元数据，runner、帮助、文档和入口审计共用同一来源；旧命令保留兼容别名。

验收：帮助／预览不产生副作用；隔离夹具验证错误参数与前置条件；文档不把“可执行”写成“已在主力机通过”。

## W2：跨机器交付证据

设计一份最小交付记录，关联提交、构建标识、必要测试、执行机器、模型／运行环境、安装结果及仍待人工验收项目。

- 将办公机通过与主力机通过分别记录；未知、未运行、失败、通过不可混用。
- 重用已有 runtime 日志、测试产物和发布清单，只做索引，不复制多套报告。
- 构建变化后使相关旧证据失效；纯文档修改不触发无关全量重跑。
- 断网、失败续跑和回滚时仍能追溯到实际产物，避免把最新文档时间当成最新构建证据。

验收：用同一提交跨两个隔离环境演练交接；故意混入旧构建时能识别不匹配。真实安装和模型验收仍需对应机器完成。

## D1：内容实体与字段归属

先绘制只读关系表，至少覆盖人物档案、热门生成身份、服装、通用场景、角色蓝图、主题、参考标准／索引、样张清单、精选与退役条目。

- 为字段说明来源、用途、权威维护位置和派生方式。`characters.json` 与热门生成身份不强行合并，先区分展示资料与模型输入。
- 同义重复字段在确认语义后由构建产生投影；不把不同用途的 prose、tokens、角色资格、场景分级和样张分级机械归并。
- 明确 ID 稳定性和作用域：服装 ID 按所属角色解析；重命名、退役和兼容别名不能破坏已有作品／深链。
- 盘点已有字段校验、测试和运行时解析，补 schemaVersion 与结构规则时尽量复用单一契约，不另建互相矛盾的校验体系。
- 确认源数据与生成产物的写入边界，双向导入保持显式预览，防止旧聚合覆盖新分片。

验收：选取工作室角色、普通热门角色、多服装角色及退役场景，逐一走通查找源数据、关系解析和构建过程。未改变现有内容语义及生成请求。

## D2：变更影响预览与增量检查

复用现有维护入口，先实现只读影响报告：输入角色／服装／场景 ID 或 Git 变更，列出关联蓝图、参考条目、主题、精选、样张及需要重建的产物。

- 报告区分必改、需复验和仅关联；不自动批量重写关联内容。
- 检查重复 ID、未知引用、默认服装、退役引用、缺失元数据及源／产物失配；承认已有检查，补实际盲区。
- 可证明影响边界时运行增量检查；公共契约和构建器变化回到全量结构验证。
- 推荐入口与参数必须来自注册表；新增维护命令同步登记工作流和文档。

验收：隔离夹具中修改一个角色或服装，报告准确列出影响对象；无关系列不被误判为必须重写；故意制造悬空引用和旧产物能被发现。

## D3：质量状态与来源证据

区分三类结果：结构合法、内容人工审核、资产实际交付。沿用现有 pending／审核／发布状态，先做映射和缺口分析，再决定是否需要新字段。

- 记录来源、审核时间、适用对象版本和资产证据；历史审核不能自动覆盖后续内容修改。
- 内容字段发生变化时，只标记受影响证据待复验，不擅自替换已发布资源。
- 模板化、重复或疑似矛盾内容只产生候选清单，交人工判断；不自动删除、合并或补写。
- 优先对高频、招牌和用户指出的问题做小批次维护，避免为统一格式发动全库改写。

验收：同一条目可以明确呈现“结构通过但缺图”“有图但未审核”等情况；原文件存在、索引有 URL 和模型出图质量不得相互替代。

## D4：安全维护与发布演练

围绕新增、修改、退役、导入四类操作，设计预览 → 校验 → 受控写入 → 构建 → 证据 → 发布／回滚的标准路径。

- 用隔离副本验证中断、重入和回滚，保存文件哈希及变更摘要；避免整个共享目录回滚覆盖别人的修改。
- 确认 manifest 和资源版本能够对应，避免旧资源与新索引混装。
- 提示词／蓝图／服装绑定变更按项目要求核对真实编译及出图；`prompt-pinned-scenes.json` 继续保持字节级保护。
- 默认不删除或迁移外部参考目录、用户作品和历史候选。资产去重／清理只提出候选，先证明引用关系与可恢复性。

验收：能从一次失败的隔离内容更新回到原版本；受保护字段和无关数据字节不变；真实发布前有可审核清单。

## D5：场景新增与稳定分片

本项针对开发侧维护项目自带场景库。当前安装模式拒绝 `/api/maintenance/scenes` 写入；用户在安装版自建场景属于另一项产品能力，应接用户数据仓储，不能通过解除项目源数据维护限制实现。

本轮只读发现：

- 通用场景按角色／系列分组，每批默认 50 条；维护源与浏览器读取分片已分离，应保留这个基础。
- `useSceneEditorModal` 新增和复制时在前端按当前列表最大 ID 加一；保存接口只接受三位数字 `scNNN`，场景数组上限 1000，蓝图数组上限 2000。扩大容量前需同时核对所有调用者和规则，不直接改变既有 ID。
- 保存接口接收完整场景集；未携带读取基线版本的旧快照需要防覆盖。现有备份与失败恢复机制要保留，但它们不替代版本冲突检测。
- `writeSceneShards` 会按 ID 排序重切整个分组；中间插入／退役可能让后续批次条目移动。`targetFile` 以分类文字是否包含 After_Story 判断归属，应避免展示分类改名意外改变物理分组。
- 分批发现逻辑从 `.1.json` 连续读取，遇到缺号即停止；应检查清单完整性与孤立后续分片，防止把损坏目录视为完整数据。

建议按以下顺序完善：

1. 统一由写入侧分配或确认稳定 ID，检查已存在和已退役 ID，不复用旧身份；并发创建在同一受控写入事务／锁内处理。兼容现有 scNNN，另设计越过 sc999 的格式及所有消费者迁移。
2. 单条新增／修改提交明确的变更集与预期版本。旧版本冲突返回可解释差异；全量导入保留为单独操作，不能与普通保存混为一谈。
3. 显式定义维护分组与场景实体关系，将文件批次作为存储细节。新增条目写入所属分组的稳定目标，仅必要时新开批次；日常新增不自动重新平衡所有文件，重分片另走显式维护流程。
4. manifest 明确可验证的分片集合与顺序，检查缺号、孤立分片、重复 ID、路径和归属冲突；文件写入原子性之外，还需验证多文件更新中断和恢复。
5. 新增前显示所属角色／服装／分组、结构校验和关联影响；创作内容逐条编写。结构通过只表示可继续审核，真实编译／出图和定稿保护仍遵循项目约束。

验收：以临时内容副本覆盖两个旧版本同时创建／保存、退役最高 ID 后再新增、达到批次边界、分片缺号、容量边界及写入中断。正常新增只改变必要源文件与生成产物，既有 ID、顺序契约、深链和受保护内容不变；未审核新内容不得混入已通过的样张状态。

不默认改成一个场景一个文件，不迁移静态内容数据库，不更改现有数据或打开安装版源数据写入口。新 CLI 命令或 API 在实现时按现有工作流和工程契约登记。

**第一批实施记录（2026-09-12，办公机）**：

- `scripts/lib/scene-write.js`：写入侧稳定 ID 分配（排除活跃＋已退役，越过 sc999 显式报错）、源分片完整性校验（缺号＋后续分片、孤立分片、单文件与批次并存、跨分片重复 ID、char 归属冲突）、增量分片写入（改动留原文件、新增追加批次、满批新开、清空批保留空文件、char 变化才跨组移动、展示分类改名不迁移物理分组）、保存事务锁（单进程串行化）。
- `routes/maintenance.js`：`GET /api/maintenance/scenes-state` 返回内容版本＋下一个稳定 ID；`POST /api/maintenance/scenes` 要求 `baseVersion` 读取基线，旧快照返回 409 并附可解释差异（serverOnly／changed／clientNew），保存前先过完整性校验，写入走增量路径，回执带 `added/updated/removed/version`；桌面打包模式两个端点均 501。
- `classify-scene-ratings.js`、`optimize-scenes.js` 的 `--write` 同步改走增量写入，保存链不再整体重切；全量重切仍归 `split-scenes.js`／`clean-scenes.js` 显式维护。
- 前端：新增／复制场景向服务端申请 ID（失败回退本地推算）；保存携带加载时锁定的基线版本，成功后采纳回执版本，409 冲突提示先「重新读取」。
- 隔离测试：`scripts/tests/test-scene-write.js`（unit，19 例）与 `scripts/tests/test-scene-maintenance-save.js`（contract，8 例）覆盖临时夹具下的冲突、退役复用、批次边界、回滚与桌面 501；`npm run check`、unit 520 例、contract 26 文件、frontend 629 例通过。真实出图不涉及本批改动，无设备验收缺口变化。
- 剩余：变更集提交协议（D5.2 的单条新增／修改只提交变更集，全量导入单列）、越过 sc999 的 ID 格式与消费者迁移、与 D2 影响预览的新增前影响展示衔接。已知限制：内容版本哈希覆盖 13 个浏览器产物（与客户端视图一致），不覆盖源分片本身的改动；保存后维护脚本若改写内容，客户端草稿与服务器可能存在内容差，下次保存不被 409 拦截（与既有行为一致，待变更集协议解决）。

## R1：安装包与图片资源分层分发

用户关切：不打包角色图片会导致初次进入空白，全量打包又会随人物和场景增长不断扩大安装包。目标是离线首次进入有完整的基础展示，高清资源按需补充，程序更新不重复携带全部图片。

本轮文件体积盘点：`assets/characters/thumbs` 160 个文件约 2.69 MiB；`assets/characters` 其他文件 174 个约 258.04 MiB；`assets/live2d` 约 66.90 MiB。这里是本机源文件大小，不是压缩安装包大小，也不包括外部参考库。发布前重新统计，不能直接作为下载体积承诺。

现状：桌面暂存复制 assets，已排除 `character-references`；角色缩略图与部分错误占位已有实现，但高清图按需下载、完整离线回退和资源包管理仍需设计。不能只从打包列表删除图片就宣布完成。

建议分层：

| 层级 | 随程序提供的内容／独立内容 | 用途 |
| --- | --- | --- |
| 必需基础资源 | 品牌、图标、占位、全角色缩略图、首屏关键图片 | 断网首次安装也能浏览目录、识别角色 |
| 基础展示图 | 每位已有合格立绘角色的一张适当分辨率预览；是否随包取决于尺寸实测 | 详情页能展示人物，高清未下载时无需留下大片空白 |
| 高清图片资源 | 高清立绘、服装参考、场景样张，按角色／系列或单资产组织 | 查看时按需补充，也可选择预下载供离线使用 |
| 成套运行资源 | Live2D 模型与其全部纹理、动作、物理等依赖 | 以完整版本安装验证，避免单文件下载造成半可用模型 |

实施顺序：

1. 建立被页面实际引用的必需资源清单。基础展示图先用已有合格图片派生并做双主题及 4K 150% 视觉审查；缺少真实原图的角色继续明确标记待补，不能用占位冒充资产完成。
2. 统一资源解析：优先匹配版本的本地高清文件，缺失时使用随包基础图，再回退到明确占位；请求失败不持续显示骨架或空白。4K 大图展示选择合适资源，列表无需加载原图。
3. 设计独立资源 manifest：稳定资产 ID、版本、尺寸、字节数、内容哈希、依赖及兼容范围。哈希验证内容完整性，可信清单／发布来源另行验证；不把二者混淆。
4. 确定下载来源、托管容量／流量预算及离线导入方式后，再实施下载。支持取消、失败重试、临时文件验证后原子就位；资源包不得覆盖任意路径或携带可执行更新逻辑。
5. 资源保存在可写用户数据目录，与程序文件和用户作品分离。程序升级保留已安装资源；按哈希或版本只下载发生变化的资产。下载／清理保留已有分级与访问控制，不因资源服务绕过本机边界。
6. 区分可重新下载的缓存与用户明确保留的离线资源。清理不能删用户作品、手工导入原图或必需基础资源；离线包不默认自动淘汰。
7. 在展示回退与交付链路通过后，才调整安装包资源清单。先提供离线可用的基本版本，再决定是否提供单独的完整资源包。

验收：全新隔离安装与断网场景不依赖开发机素材目录；首页、角色列表、角色详情有基础展示；高清缺失状态清楚。另覆盖损坏下载、取消／中断、磁盘不足、重复下载、资源更新失败、程序升级保留资源和离线导入。分别记录程序包、基础资源、可选资源和首次必要下载的体积。体积预算以实际样本与视觉质量决定，不预先承诺固定压缩率。

边界：本阶段涉及下载及资源管理行为，属于待实施的明确功能范围；当前仅规划，不配置外部托管、不上传图片、不删改打包资源，不静默触发大资源下载。

## 可继续规划，但不默认启动

| 方向 | 启动依据 | 首个交付 |
| --- | --- | --- |
